# Соглашения для моделей запросов

Сверяй модель со схемой `schemas/schema.yaml` и похожими классами в этой папке. Учитывай существующие
расхождения между схемой и реализацией. Примеры: `BotCommand`, `Button`.

## Создание и хранение данных

- Конструктор и `new()` принимают одинаковые аргументы с одинаковыми значениями по умолчанию. `new()` вызывает
  конструктор. `make()` требует поля, обязательные для создания модели, когда их можно выразить аргументами.
  Для альтернативных полей используй именованные фабрики, как в `PhotoAttachmentRequestPayload`.
- Конструктор записывает напрямую только неизменяемые поля; остальные передаёт сеттерам. Не дублируй в нём
  проверки сеттеров.
- Описывай собственные поля модели в типе `$data` как array shape. Не повторяй унаследованные поля.
  Отсутствующие поля обозначай `?`; вложенные списки и объекты тоже типизируй.
- Для массивов из схемы используй `list` или `non-empty-list` при `minItems > 0`. В аргументах конструктора
  и сеттеров принимай `array` или `non-empty-array`, а перед записью списка в `$data` вызывай `array_values()`.
- Поля с `additionalProperties` описывай типом, соответствующим фактическому формату данных.
- Поля `notify` и `quick` сохраняй в `$data` как обязательные, если у них есть значение по умолчанию.
- `deprecated` поля не добавляй в новые модели. Не меняй схему автоматически при работе над моделью.
- Даже если схема или документация допускает `null`, не передавай его в запросе: вместо этого опускай поле.
  В `$data` не сохраняй `null`; такие поля описывай необязательными ключами (`field?: Type`), без `|null`.
  Аргументы конструктора и фабрик могут принимать `null` как указание не добавлять поле.

## Методы и проверка

- Для поля, которое можно установить после создания, добавляй нужные `get`, `set` и `isset` методы.
  `unset` добавляй только для поля, которое может отсутствовать в `$data` и которое разрешено удалять.
- Аргументы сеттеров обязательны. Проверяй в сеттерах ограничения схемы: `minLength`, `maxLength`,
  `minItems`, `maxItems` и `pattern`. Подключай `ValidateTrait` только при использовании его методов.
- Используй `ValidateRequiredTrait`, когда нужна проверка обязательных полей или выбора одного из полей.
  Настраивай `$required` или `$requiredOnce` до записи данных; в наследуемом классе дополняй список.
  Поле, всегда записываемое конструктором, повторно проверять не нужно.
- Поле с `discriminator` делай доступным только для чтения.
- Для методов, возвращающих текущий объект, указывай `@return $this`.

## Типы и документация

- Сохраняй ограничения, которых нет в типах PHP, в PHPDoc/Psalm: `non-empty-string`, `non-negative-int`,
  `positive-int`, диапазоны чисел, array shape. Для Unix timestamp используй `non-negative-int`.
- Ограничения длины и числа элементов, не выраженные типом, помещай в скобках в конце первого предложения
  описания значения. `minLength: 1` и `minItems: 1` уже выражены типами и повторять их не нужно.
- В геттерах и методах `isset*` и `unset*` не добавляй текстовые описания. В PHPDoc геттеров оставляй
  только необходимые аннотации расширенных типов. Описания значений сеттеров помещай в `@param`.
- Для полей `token`, `code` и `message_id`, которые должны быть непустыми, используй `non-empty-string`
  и `validateString()`.
